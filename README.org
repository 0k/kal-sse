#+TITLE: kal-sse

Resilient Server-Sent Events: snapshot + cursor data channels with
gap-free reconnect.

* What it is

A *data channel* pairs a REST snapshot with an SSE update stream. One
=sub_id= identifies one logical subscription to one data flow, not a
tab, window, or application.

The snapshot is subscription birth or reset. =register(sub_id)= and
=register_at(sub_id, now)= mint the id or adopt a proposed hyphenated
UUID (anything else is replaced by a fresh id), supersede any prior
handle, record the current index as the snapshot base, and set the
server cursor to that base. TTL starts at registration and lasts until
the first stream attach.

The stream is =GET <stream>?sub=<uuid>[&last_event_id=<n>]=, or uses
the =Last-Event-ID= header. The header wins. The server caps the
client's last applied id at the server cursor, replays retained events,
and atomically attaches the live stream. An id below the snapshot base
gets =409 needs_snapshot=: that client never saw the current snapshot.
With no id, it resumes from the server cursor. Every event carries
=id: <index>=.

* Why not plain SSE?

Plain SSE over a fresh =tokio::broadcast::Receiver= silently loses
events during disconnection and skips gaps after receiver lag.
=kal-sse= retains replay state and answers either a complete replay or
=409 needs_snapshot=, never a silent gap.

The server cursor advances when the adapter hands an event to the HTTP
stack. A successful socket write only places bytes in the server's
kernel send buffer: =send(2)= does not imply delivery, TCP
acknowledgements are consumed by the kernel rather than reported for
each write, and an acknowledgement means only that the client kernel
buffered bytes. It does not mean the client application applied them.
After a dead connection, the server may have advanced beyond the
client's applied state. The cursor is therefore an upper bound, and the
client supplies its last applied id on reconnect.

Only disconnected handles age out. An attached stream holds its handle
indefinitely and is never TTL-expired mid-stream.

* The protocol

The adapter's =last_event_id(&headers, query)= parser accepts the
=Last-Event-ID= header or =last_event_id= query parameter. A malformed
value returns =400 bad_last_event_id=. Use
=sse_response_from(log, sub, last, serialize, hint)= to resume from the
parsed id. =sse_response= passes no id and uses only the server cursor;
it cannot recover events lost after a silent disconnect.

An =EventSource= cannot set headers. It sends =Last-Event-ID= when the
browser retries its current connection, but a newly created
=EventSource= must put the remembered id in =?last_event_id==. This is
the same idea as Mercure's query parameter.

* Wire exchanges

** Scenario A: first subscription

#+begin_example
Client                              Server
  |                                   |
  | GET /api/things                   |
  |---------------------------------->| register(None) -> (sub, base=42)
  | 200 {sub}, x-snapshot-index: 42   |
  |<----------------------------------|
  | GET /api/things/stream?sub=sub&   |
  |   last_event_id=42                |
  |---------------------------------->| attach_from(sub, Some(42))
  | 200 OK (SSE stream)               |
  |<----------------------------------|
  | id: 43                            | advance(43) at HTTP hand-off
  |<----------------------------------|
#+end_example

The live receiver is subscribed before backlog is read under the same
lock, so no event can slip between replay and live delivery.

** Scenario B: dead connection and replay

#+begin_example
Client                              Server
  | id: 44 (applied)                  |
  |<----------------------------------|
  | id: 45 (handed to HTTP stack)      | advance(45)
  |<----------------------------------| [connection dies before apply]
  | GET ...?sub=sub&last_event_id=44  |
  |---------------------------------->| attach_from(sub, Some(44))
  | id: 45                            | replay
  |<----------------------------------|
  | id: 46                            | replay or live tail
  |<----------------------------------|
#+end_example

Events already sent remain replayable for
=DEFAULT_REDELIVERY_WINDOW= after being sent, 60 seconds or four
15-second keep-alives.
=with_redelivery_window= changes that window. =max_events= remains a
hard cap.

** Scenario C: resume failure and re-snapshot

#+begin_example
Client                              Server
  | GET ...?sub=sub&last_event_id=44  |
  |---------------------------------->| UnknownSub or Expired
  | 409 {"error":"needs_snapshot"}   |
  |<----------------------------------|
  | GET /api/things?sub=sub            |
  |---------------------------------->| register(Some(sub)) -> new base
  | 200 {sub, snapshot}                |
  |<----------------------------------|
#+end_example

=AttachError::UnknownSub= means the id was never registered, TTL was
reclaimed, compaction forgot an unattached unresumable handle, or the
server restarted. =AttachError::Expired= means the requested backlog
left retention and the =409= body adds =earliest= and =current=.

** Scenario D: supersede race

#+begin_example
Client A                            Client B                 Server
  | stream epoch 1                    |                         |
  |                                   | GET snapshot?sub=sub    |
  |                                   |------------------------>| register bumps epoch
  |                                   | GET stream?sub=sub&     |
  |                                   |   last_event_id=<index> |
  |                                   |------------------------>| attach bumps epoch
  | [ends on its next live event]     |                         | epoch 1 is stale
  |<----------------------------------X                         |
#+end_example

Re-registering or re-attaching a =sub_id= bumps its epoch. The
superseded stream's =advance= and =disconnect= become no-ops; it ends
when its next live event observes that it is stale. At most one live
attach is authoritative.

A =sub_id= belongs to one client at a time; give each tab its own. If
client A reconnects anyway, with a last id older than B's snapshot, it
gets =409 needs_snapshot= and re-takes the snapshot, which supersedes B
in turn. Sharing stays unsupported: the clients keep superseding each
other, and one that opens its stream without a last id can miss events.

* Client requirements

A client applies events in order and stores the last applied =id=. A
native browser =EventSource= hides a non-200 response, including the
=409= status, so a client must also detect a resume attempt that never
opens and return to snapshot recovery.

** Client loop

#+begin_example
1. GET the snapshot endpoint, proposing the stored sub_id.
   Render the snapshot, store the returned sub_id, and take the
   snapshot index (x-snapshot-index header) as the last applied id.
   A cross-origin snapshot endpoint must send
   Access-Control-Expose-Headers: x-snapshot-index.
2. Open GET <stream>?sub=<sub_id>&last_event_id=<last applied id>.
3. Apply events in order and remember the last applied id.
4. On a drop, reconnect with the same sub_id and last applied id in the
   query parameter or header.
5. On 409, or a resume attempt that never opens, return to step 1 with
   the same sub_id.
#+end_example

* Server usage

#+begin_src rust
use std::sync::{Arc, Mutex};
use std::time::Duration;

use axum::extract::{Query, State};
use axum::http::HeaderMap;
use axum::response::IntoResponse;
use axum::routing::get;
use axum::{Json, Router};
use kal_sse::axum::{last_event_id, sse_response_from, SNAPSHOT_INDEX_HEADER};
use kal_sse::core::EventLog;
use serde::Deserialize;
use tokio::time;

#[derive(Clone)]
struct AppState {
    log: Arc<Mutex<EventLog<String>>>,
}

#[derive(Deserialize)]
struct SnapshotQuery {
    sub: Option<String>,
}

#[derive(Deserialize)]
struct StreamQuery {
    sub: String,
    last_event_id: Option<String>,
}

async fn snapshot(
    State(state): State<AppState>,
    Query(q): Query<SnapshotQuery>,
) -> impl IntoResponse {
    let (sub_id, cursor) = state.log.lock().unwrap().register(q.sub);
    let mut headers = HeaderMap::new();
    headers.insert(SNAPSHOT_INDEX_HEADER, cursor.to_string().parse().unwrap());
    // Return headers + snapshot body (abbreviated here).
    (headers, format!("{{\"sub\":\"{sub_id}\"}}"))
}

async fn stream(
    State(state): State<AppState>,
    headers: HeaderMap,
    Query(q): Query<StreamQuery>,
) -> Result<impl IntoResponse, (axum::http::StatusCode, Json<serde_json::Value>)> {
    let last_event_id = last_event_id(&headers, q.last_event_id.as_deref())?;
    sse_response_from(
        state.log.clone(),
        q.sub,
        last_event_id,
        |e: &String| e.clone(),
        "resync via GET /api/things",
    )
}

#[tokio::main]
async fn main() {
    let log = Arc::new(Mutex::new(EventLog::<String>::new(
        Duration::from_secs(900), // TTL of a handle with no attached stream
        10_000,                   // max retained events
        256,                      // broadcast channel capacity
    )));

    // Periodic compaction: reclaim expired handles, trim the buffer.
    let compact_log = log.clone();
    tokio::spawn(async move {
        let mut tick = time::interval(Duration::from_secs(60));
        loop {
            tick.tick().await;
            compact_log
                .lock()
                .unwrap()
                .compact(std::time::Instant::now());
        }
    });

    // Appender (example: append from some external source).
    let append_log = log.clone();
    tokio::spawn(async move {
        let mut tick = time::interval(Duration::from_secs(5));
        loop {
            tick.tick().await;
            append_log.lock().unwrap().append("hello".to_string());
        }
    });

    let state = AppState { log };
    let app = Router::new()
        .route("/api/things", get(snapshot))
        .route("/api/things/stream", get(stream))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}
#+end_src

The snapshot handler registers the subscription. The stream handler
parses the last applied id, uses =sse_response_from=, and returns its
=400= or =409= responses directly. Call =compact= periodically.

* Retention and memory

=compact= removes TTL-lapsed handles and unattached handles whose next
needed event has already left the buffer. Retention keeps events after
the lowest resume floor of surviving handles, plus recently sent events
within the redelivery window. =max_events= is a hard cap and may make a
backlog unavailable.

On broadcast lag, the adapter ends the stream without advancing past
the gap. The client reconnects from its last applied id and gets a full
replay or =409 needs_snapshot=.

* Scope and limits

- *In-memory, single-process.* Restart loses handles and requires a new
  snapshot.
- *Not horizontally scalable as-is.* The registry and event buffer are
  process-local.
- *Slowest surviving handle pins retention.* The hard cap bounds memory
  by making old backlogs expire.

* Multiplexed connections

Carrying many channels over one SSE connection, with in-stream
snapshots and live add/remove of channels, is implemented in =mux=
(feature-free core) and =mux_axum= (feature =axum=), as specified in
[[file:doc/mux.org][doc/mux.org]]. Async opens and streamed snapshot parts
keep slow-loading channels independent. Existing
single-channel APIs are unchanged.

Short server setup (the full runnable example is
[[file:examples/mux.rs][examples/mux.rs]], including curl commands):

#+begin_example
use std::sync::Arc;
use std::time::{Duration, Instant};
use kal_sse::{EventLog, mux::{Channel, Mux, MuxConfig, MuxSource}};

let counter = Arc::new(Channel::new(
    0_u64,
    EventLog::new(Duration::from_secs(900), 1024, 16),
    |value| Ok(vec![value.to_string()]), // one serialized JSON snapshot part
));
let source = counter.clone();
let mux = Mux::new(MuxConfig::default())
    .family("counter", move |_: Option<&str>| {
        Ok(source.clone() as Arc<dyn MuxSource>)
    })?;
let app = axum::Router::new()
    .nest("/mux", kal_sse::mux_axum::router(mux.clone()));

// Change state and append its delta under the SAME channel lock:
counter.update(|value, log| {
    *value += 1;
    log.append(value.to_string());
    log.compact(Instant::now());
});
mux.compact(Instant::now()); // also run periodically, even without appends
#+end_example

Existing typed logs do not need to become =EventLog<String>=. A custom
=MuxSource= can share =Arc<Mutex<EventLog<E>>>= with existing
single-channel endpoints. Set =serialize: EventSerializer<E>= to an
=Arc= serializer (for example =Arc::new(u32::to_string)=). The following
two method bodies illustrate a numeric state behind a separate mutex;
the remaining source methods delegate to that same typed log:

#+begin_example
use kal_sse::mux::{erase_replay, open_on_log, ErasedReplay, Opened};
use kal_sse::{AttachError, Cursor};

fn open_fresh(&self, now: Instant) -> Result<Opened, String> {
    let state = self.state.lock().expect("state mutex poisoned");
    let parts = vec![state.to_string()];
    let mut log = self.log.lock().expect("event log mutex poisoned");
    // Keep state AND log guards through registration + attachment.
    open_on_log(&mut log, parts, self.serialize.clone(), now)
}

fn resume(&self, sub: &str, hint: Option<Cursor>)
    -> Result<ErasedReplay, AttachError>
{
    let replay = self.log.lock().expect("event log mutex poisoned")
        .attach_from(sub, hint)?;
    // The typed replay already owns its backlog/live boundary.
    Ok(erase_replay(replay, self.serialize.clone()))
}
#+end_example

Writers must use the same state -> log lock order. Hold every lock under
which the state and log change from snapshot rendering until
=open_on_log= returns. For a store that already performs flush -> build
snapshot -> register, keep its store guard through =attach= too, then
construct =Opened= with =erase_replay=; do not register a second time.
Erasure serializes the bounded backlog immediately and live events only
when received; it spawns no task. Serializers must not re-enter the mux
or acquire locks held by their caller. =Channel<S>= remains the simple
single-lock, already-serialized alternative.

** Asynchronous and streamed snapshots

Existing =open_fresh= implementations work unchanged: =MuxSource::open=
wraps them in a future ready on its first poll, preserving synchronous
attachment timing (the mux polls once when attaching).
For a slow cache bootstrap, override =open= instead. It returns an owned
=Send + 'static= future; clone the state needed by that future:

#+begin_example
use kal_sse::mux::{OpenFuture, SnapshotParts};

fn open(self: Arc<Self>, _attempt_started: Instant) -> OpenFuture {
    let cache = self.cache.clone();
    Box::pin(async move {
        cache.wait_until_ready().await?;
        // Application method: under the writers' state/log locks, capture
        // immutable snapshot state, register + attach, then release locks.
        let mut opened = cache.open_fresh(Instant::now())?;
        let parts: SnapshotParts = std::mem::take(&mut opened.snapshot).into();
        Ok(opened.with_snapshot(parts))
    })
}
#+end_example

To produce parts over time, replace the ready =parts= above with
=SnapshotParts::new(move |cx| receiver.poll_recv(cx))=, where the receiver
yields =Option<Result<SnapshotPart, String>>= (for example a Tokio mpsc
receiver owned by the source). The mux creates no task or queue: providers
can also poll an I/O stream or incremental serializer directly. Each
=SnapshotPart { data, last }= is one frame; the final part MUST have
=last: true=. Premature EOF or an error produces =channel_error= with a
reason, releases the handle, and leaves other channels running.

The source decides when the snapshot barrier happens, normally AFTER
loading. Every part must describe the SAME immutable state at that cursor,
not live state read at different times. The log receiver attaches at the
barrier; deltas wait until the last part and recover from log replay after
lag. Pending opens/parts yield their scheduler turn to other channels and
must register the supplied waker. Calls and polls must not block or hold
source locks across awaits.

Cancellation is ownership-based. Before returning =Opened<SnapshotParts>=,
the future must release any handles it created if dropped or errored (use
an RAII guard if taking the barrier before an await). After success, the
mux owns cleanup. Remove cancels loading/parts, releases the handle and
emits =removed=; re-add uses a new generation. Disconnect cancels pending
opens; reconnect retries them under a new generation. A partially delivered
snapshot also restarts under a new generation on reconnect.

** Routes and delivery

The nested routes are =POST /mux= (reserve), =GET /mux/stream?conn=…=
(stream), =POST /mux/{conn}/channels= (add/remove), and
=DELETE /mux/{conn}= (release). Protect them with application
authentication. Opens start when the stream attaches, not at reservation;
asynchronous sources may take their snapshot later. Payload strings must contain valid serialized JSON;
the HTTP adapter embeds them verbatim.

Core callers use =MuxStream::next().await= or =poll_next=; with =axum=
enabled, it also implements =futures_core::Stream=. Do not prefetch:
returning a frame is the cursor hand-off boundary. A reconnect supplies
=resume={"counter":[generation,last_applied_cursor]}= as a URL-encoded
query parameter. Missing or stale hints trigger a new snapshot only for
the affected channel. Removal releases the handle immediately; dropping
the stream starts the connection and channel TTLs. The bounded removal
acknowledgement queue refuses an overflowing change atomically with
=429= and a reason; drain the stream and retry that change.
